> Этот файл — **каноничный шаблон** отчёта по ROI-видеоаналитике для цеха №1.
> Любой ИИ-агент или скрипт, который формирует отчёт по `ceh1_roi_stats.json`,
> должен следовать структуре ниже.

- Данные лежат в `exports/ceh1_roi_stats.json` (выгрузка делается ИИ-агентом из `exports/postgres` — PGDATA с другого ПК).
- Камера id=2, имя "цех1", 3 ROI-зоны.
- Окно анализа: 07:00–19:00 (12-часовая смена).

### Новые таблицы (появились в дополнение к ROI-таймерам)

Теперь БД хранит **два слоя метрик**:

**Слой A — ROI-таймеры (было, осталось):** "работа / простой" по каждой ROI-зоне
- `roi_timers`, `roi_timer_daily`, `roi_timer_hourly`, `roi_timer_events`

**Слой B — Подсчёт людей (новое):** "сколько людей в зоне сейчас" — occupancy
- **`roi_people_counters`** — текущее состояние **по каждой ROI**. Поля: `current_workers` (0..max), `max_workers=2`, `seconds_0_workers` / `seconds_1_worker` / `seconds_2_workers` (сколько секунд проведено с таким количеством людей)
- **`roi_people_daily`** — то же **по дням**, PK = `(camera_id, roi_key, day_date)`
- **`roi_people_events`** — **события** изменения количества работников: `workers_before → workers_after`, `event_type` ('enter'/'leave'/etc), `ts`, есть индекс `(camera_id, roi_key, ts)`
- **`people_zone_counters`** — **бегущие счётчики по всей камере** (без разбивки по ROI). `max_workers=3`, счётчики на 0/1/2/3 работников
- **`people_zone_daily`** — то же по дням
- **`people_zone_events`** — события по камере

### Что это даёт для аналитики

- **Было:** только "работает ли зона" (да/нет + длительность)
- **Стало:** + **сколько людей** в зоне одновременно, **как меняется** число людей, **доли времени** с 0/1/2/3 работниками
- Можно строить occupancy heatmap ("когда сколько людей на участке")

### Что осталось прежним

- 7 "старых" таблиц не тронуты: `cameras`, `departments`, `faces`, `roi_timers`, `roi_timer_daily`, `roi_timer_hourly`, `roi_timer_events`
- Креды БД и подключение (`localhost:7032`, user=didi) без изменений
- `ceh1_roi_stats.json` (выгрузка для директорского отчёта) собирается по **той же** логике, что и раньше — только ROI-таймеры

## Что считается "рабочим днём"

**Будни по календарю РФ**, исключая:
- Субботы и воскресенья
- 12.06 (День России) — официальный праздник

**Неполные дни** (первый день статистики, день выгрузки) тоже исключаются из средних.

В текущем массиве данных неполные = `2026-06-03` (старт) и `2026-06-17` (день выгрузки).

## Структура отчёта (обязательная)

1. **Шапка** — кому, период, окно анализа, дата формирования (ISO с таймзоной +04:00)
2. **Краткая выжимка** — 7 пронумерованных тезисов:
   1. Сколько полных рабочих дней проанализировано
   2. Зона-лидер (с цифрами)
   3. Зона-аутсайдер (с пометкой "требует внимания")
   4. Нестабильная зона (диапазон мин-макс)
   5. Лучший день цеха с %
   6. Слабый день цеха с %
   7. Сколько отклонений от нормы выявлено
3. **Сводка по зонам** — таблица: Зона | Ср. работа | Ср. простой | Загрузка % | Мин | Макс + интерпретация по каждой зоне
4. **Рейтинг зон** — нумерованный список по убыванию загрузки
5. **Лучшие и худшие дни по зонам** — отдельный блок для каждой зоны
6. **Отклонения от среднего** — список с датами, цифрами и оценкой ("критически низкая", "необычно высокая", и т.п.)
7. **Ключевые наблюдения для решений** — 5-6 пунктов, что делать руководству
8. **Исключённые дни** — отдельный блок с обоснованием
9. **Футер** — одна строка про источник данных

---

## Форматы

- **Время:** `H:MM:SS` (например `3:23:56`, `0:49:53`)
- **Процент загрузки:** один знак после запятой, **bold** (`**28.3%**`)
- **Даты:** `YYYY-MM-DD`
- **Эмодзи:** только 📈 📉 🔥 ⚠️ 🟢 🟡 🟠 🔴 (статусы и тренды)
- **Дни недели:** сокращённо в скобках после даты `(пн)`, `(вт)`, `(ср)`, `(чт)`, `(пт)`, `(сб)`, `(вс)`

---

## Ключевые наблюдения — что обязательно подсветить

1. **Дисбаланс между зонами** — разница между лидером и аутсайдером (обычно 3×)
2. **Нестабильные дни** — где зона резко упала или выросла относительно соседних дней
3. **Аномалии выходного дня** — если в выходные зафиксирована работа (сверхурочные/спецзаказ)
4. **Лучший и худший день** — с привязкой к плану производства
5. **Рекомендация** по зоне-аутсайдеру (проверить геометрию ROI, реальную загрузку)

---

## Правила

- **Не придумывать цифры** — только из `ceh1_roi_stats.json`
- **Не делать выводов** о причинах без пометки "возможно", "стоит проверить"
- **Не упоминать** другие камеры (cam1, cam3) — отчёт только по цеху №1
- **Не использовать** эмодзи-кружочки 🟢🟡🟠🔴 в шапке сводки — только в таблице зон (по статусу)
- **Не использовать** слово "поток" — только "смена", "зона", "рабочее место"
- **Все цифры** должны быть в формате `H:MM:SS` (даже если это `0:02:00`)

## ⚠️ Обновлено 2026-07-02 — добавлен AI чат-виджет

### Что это

В правом нижнем углу detect_face frontend (`http://localhost:8081/`) теперь синяя
кнопка **AI**. По клику открывается чат-панель, в которой можно спросить что угодно
про отчёты, ROI-зоны, статистику. На том же хосте поднят отдельный Python-сервис,
который пересылает сообщения в **Mavis general-agent сессию** — то есть пользователь
виджетa общается **с тем же агентом**, что и в MiniMax Code, со всеми его инструментами
(Read/Glob/Grep/Bash + доступ к `C:\Users\Dudu\Desktop\detect_face\`).

### Где что лежит

```
C:\Users\Dudu\detect_face_chat\                  ← чат-бэкенд (на хосте, не в Docker)
├── server.py                                     ← Python stdlib http.server, порт 9876
├── run_chat.bat                                  ← запуск (использует Python 3.12)
├── README.md                                     ← подробная инструкция
├── static\
│   ├── chat.js                                   ← vanilla JS виджет (кнопка + панель)
│   ├── chat.css                                  ← стили demo-страницы
│   └── index.html                                ← demo-страница для проверки
└── logs\
    └── chat-server.log

C:\Users\Dudu\Desktop\detect_face\frontend\
├── chat.js                                       ← КОПИЯ виджета (та что грузится в браузере)
└── index.html:834                                ← <script src="/chat.js?v=1"> перед </body>
```

### Архитектура

```
detect_face frontend (8081, nginx, Docker)
  ↓ грузит /chat.js
  ↓ клик на 💬 → POST http://localhost:9876/api/chat
              ↓
detect_face_chat server.py (9876, на хосте)
  ↓ subprocess: mavis.cmd communication send --to <general-session> --command prompt
              ↓
Mavis daemon (localhost:15321)
  ↓
general agent session (mvs_ec3954456c0d4c948852dd714fb07802)
   ↑ имеет Read/Glob/Grep/Bash + доступ к detect_face\
   ← polling mavis session messages пока finish_reason != "stop"
              ↑
server.py отдаёт ответ в JSON
              ↑
виджет рисует ответ в чат-панели
```

### Как запустить

1. Открыть `C:\Users\Dudu\detect_face_chat\run_chat.bat` (двойной клик) — запустится сервер.
2. Виджет в браузере заработает автоматически.

### ⚠️ Подводные камни (запомнить перед любыми правками)

1. **Порт НЕ 8765!** На `localhost:8765` уже сидит чужой Flask-сервис
   (`compare_weights.py`, PID 24936, Werkzeug/Python 3.12). Используем **9876**.
2. **Python НЕ из PATH!** `where python` указывает на `C:\RoboDK\Python37\python.exe`
   (Python 3.7), который падает с SyntaxError на f-strings с кириллицей.
   В `run_chat.bat` и `server.py` используется **жёстко** полный путь
   `C:\Users\Dudu\AppData\Local\Programs\Python\Python312\python.exe`.
3. **Все сообщения попадают в ОДНУ сессию mvs_ec3954456c0d4c948852dd714fb07802** —
   ту же, что у MiniMax Code. Диалог в виджете и в MiniMax Code **перемешиваются**.
   Это by design для одного локального пользователя. Для нескольких юзеров — TODO.
4. **CORS `*` разрешён** в `server.py` — на локалке норм, для удалённого доступа сузить.
5. **Сервер на хосте → переживает перезагрузку Mavis как нет.** Если daemon падает,
   чат тоже падает. Восстановление: перезапустить `run_chat.bat`.
6. **Round-trip занимает 10–30 сек** (агент думает). Если 180 сек не уложился —
   виджет показывает "Agent timeout. Try again.".
7. **mavis.cmd должен быть в** `C:\Users\Dudu\.mavis\bin\mavis.cmd` —
   server.py ищет его там по абсолютному пути (см. `_find_mavis_cmd()`).
